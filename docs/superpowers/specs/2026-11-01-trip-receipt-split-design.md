# 여행 영수증 정산 앱 — 설계 스펙

> 작성일: 2026-11-01
> 상태: 설계 확정. 이 스펙을 검토한 뒤 구현 계획을 작성한다.

## Context
- **기준:** 1차 프로젝트 가이드(`docs/context/…1차_프로젝트_가이드.pdf`)
  - 핵심 흐름 하나를 실제 데이터 여러 건으로 끝까지 돌린다.
  - 지표 1개 이상으로 개선 전후를 비교한다.
  - 안정성 방어를 2가지 이상 시연한다.
  - AI 활용 과정을 기록한다.
- **직군:** 개발. 발표의 중심 질문은 "어떻게 동작하는가"이고, 구조·오류 처리·프롬프트 버전 비교로 답한다.
- **문제:** 여행이 끝나면 총무가 영수증 수십 장을 보고 금액과 시간을 손으로 옮겨 적는다. 그다음 "카페엔 누가 빠졌지?"를 기억에 의존해 정산한다. 회비형이든 선결제형이든 오래 걸리고 틀리기 쉽다.
- **제약:** 3일, 로그인·DB 없음(세션 상태만 사용), Streamlit Community Cloud 배포, 국내 여행(KRW)만, 인식은 Gemini Flash.

## 기술 스택
| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.12 | 가이드 도구이고, Streamlit Cloud에서 지원한다 |
| UI·배포 | Streamlit + Streamlit Community Cloud | 가이드 도구이고, Secrets로 키를 관리한다 |
| AI | Gemini Flash (`google-genai` SDK, JSON 스키마 응답) | 무료 등급이다. 배포 환경에서 호출할 수 있다 |
| 스키마 검증 | pydantic v2 | 인식 결과 검증, JSON 스키마 생성 |
| 이미지 처리 | Pillow (+ pillow-heif) | 리사이즈, HEIC 변환, EXIF 제거 |
| 좌표 변환 | 카카오 로컬 API (`requests`) | 한국 주소와 상호명 검색이 정확하다. 무료이고 키가 필요하다 |
| 지도 | folium + streamlit-folium (AntPath) | 움직이는 경로를 별도 애니메이션 루프 없이 그린다 |
| 표·평가 | pandas | 정산 표, 평가 결과 집계 |
| 테스트 | pytest | 정산 로직, 스키마 검증 |
| 키 관리 | 로컬 `.env`(python-dotenv) / 배포 `st.secrets` | 키를 저장소에 넣지 않는다 |

## 핵심 흐름 (한 페이지, 4단계)
1. **여행 설정**
   - 참석자 이름, 대표 지정
   - 정산 방식: 선결제형, 또는 회비형 + 1인 회비
   - 송금 정보: 계좌, 토스 링크, 카카오페이 링크. 돈을 받을 수 있는 사람만 입력한다.
2. **업로드**
   - 영수증과 예약 캡처 이미지를 여러 장 올린다.
   - Gemini가 인식한 뒤 시간순으로 정렬한다.
3. **검토·참석자 체크**
   - 결제 건을 카드로 보여 주고, 상호·일시·주소·금액을 수정할 수 있다.
   - 결제자는 드롭다운으로 고른다(기본값 대표).
   - 참석자는 기본 전원 체크이고, 빠진 사람만 해제한다.
   - 영수증이 없는 지출은 수동으로 추가한다.
4. **정산 결과**
   - 사람별 "낸 돈 / 부담액 / 차액" 표를 보여 준다.
   - 사람별 송금 메시지(금액 + 링크 + 계좌)를 복사할 수 있다.
   - 결과 JSON을 내려받거나 다시 불러올 수 있다.
5. **(부가) 여행 경로 지도**
   - 주소를 좌표로 바꿔 시간순 AntPath 애니메이션으로 그린다.
   - 핵심 흐름을 끝낸 뒤에 만든다.

## 정산 규칙
- **공식:** 사람마다 `차액 = 낸 돈 − 부담액`을 계산한다. 결제 건마다 금액을 체크된 참석자에게 1/N로 나눈다.
- **결제자는 결제 건마다 지정한다.** 그래서 돈을 받을 사람이 여러 명일 수 있다. 받을 사람과 보낼 사람을 그리디 방식으로 짝지어 송금 횟수를 줄인다.
- **회비형:** "회비 지갑"을 가상의 참여자로 둔다. 회비 지갑은 모든 사람에게서 회비를 받은 상태로 시작한다. 같은 공식으로 계산하면 남은 돈을 돌려줄지, 모자란 돈을 더 걷을지가 나온다.
- **회비형의 결제자 기본값:** 회비 지갑이다. 회비 카드로 결제하지 않은 건(개인이 낸 건)만 결제자를 바꾼다.
- **1원 단위 나머지:** 결제자가 부담한다. 결제자가 회비 지갑이면 지갑이 부담한다. 정산 전체의 합계가 맞는지 테스트로 확인한다.
- **차액 0원인 사람:** 송금 메시지를 만들지 않는다.
- **송금 링크:** 링크에 금액이 미리 채워지는지는 1일차에 실제 링크로 확인한다. 안 되면 "링크 + 금액 텍스트"로 보낸다.

## 인식 결과 JSON
```json
{
  "doc_type": "receipt | booking_capture | card_slip | not_receipt",
  "merchant_name": "흑돼지명가 애월점",
  "merchant_address": "제주 제주시 애월읍 ... | null",
  "paid_at": "2026-10-12T19:42 | null",
  "total_amount": 96000,
  "currency": "KRW",
  "category": "food | cafe | lodging | transport | shopping | activity | etc",
  "items": [{"name": "흑돼지 2인분", "amount": 48000}],
  "warnings": ["합계와 품목 합이 다름"]
}
```
- **total_amount:** 할인과 포인트를 반영한 실제 결제 금액이다. 프롬프트와 라벨링 규칙에 같은 정의를 쓴다.
- **카드번호·승인번호:** 추출하지 않는다. 프롬프트와 스키마 양쪽에 명시한다.
- **items:** 화면 표시용이다. 평가와 정산에는 쓰지 않는다.
- **검증:** Gemini의 JSON 스키마 응답 모드를 쓰고, pydantic으로 한 번 더 검증한다. 검증에 실패하면 1회 재시도하고, 그래도 실패하면 수동 입력으로 넘긴다.
- **시간 누락:** 예약 캡처처럼 시간이 없으면 그 날짜의 맨 앞에 정렬한다. 연도가 없으면 여행 날짜로 보정한다.
- **여행 기간 밖 날짜:** 경고만 하고 포함한다(예: 미리 결제한 숙소 예약).
- **외화 영수증:** 경고하고 제외한다.

## 인식 구조
- **공통 인터페이스:** `recognize(image_bytes, prompt_version) -> Receipt`
- **백엔드 2개:** `GeminiBackend`(실제 호출)와 `MockBackend`(저장된 JSON 반환, UI 개발용, 비용 0)
- **다음 단계로 미룸:** 로컬 VLM 백엔드(Ollama). 인터페이스는 열어 두되 이번에는 구현하지 않는다.

## 지표·테스트셋
- **주 지표:** 핵심 3필드(총액·일시·상호) 완전 일치율. 프롬프트 v1과 v2를 이 지표로 비교한다.
- **보조 지표:** 필드별 정확도, 장당 응답 시간, JSON 실패율·오류율
- **비교 규칙**
  - 상호명은 공백과 지점명을 정규화해서 비교한다.
  - 일시는 분 단위까지 일치해야 맞은 것으로 본다.
  - v2에서 바꾼 내용은 v1 실패 분석에서 나와야 하고, 그 과정을 ai-log에 기록한다.
- **테스트셋 25장:** 실물 12장 이상 + 직접 만든 샘플 13장 이하
  - 실물: 본인 영수증, 동의받은 가족·지인 영수증. 카드번호와 이름은 가린다.
  - 직접 만든 샘플: HTML 영수증 템플릿을 렌더링해 만들고, 예약 캡처 목업도 만든다.
  - 정확도는 실물과 직접 만든 샘플로 나눠서 보고한다. 직접 만든 샘플은 쉽게 맞혀서 정확도가 부풀려질 수 있다.
- **유형별 구성**
  - 식당 8, 카페 4, 마트·편의점 3, 교통·주유 2, 숙소 예약 캡처 3
  - 까다로운 경우 5: 흐림·기울어짐, 할인·포인트, 카드전표만 있음, 영수증 아닌 사진, 중복 업로드
- **파일:** 정답은 `eval/ground_truth.json`에 둔다. `eval/run_eval.py --prompt v1|v2`로 실행하고 결과를 `eval/results/`에 저장한다.
- **정산 로직:** 결정적인 계산이라 지표에 넣지 않고 pytest로 검증한다.

## 비용·한도·보안
- **목 모드와 결과 캐시:** 목 모드로 UI를 만들고, 이미지 해시로 결과를 캐시하고, 평가 결과는 파일로 저장한다. 같은 이미지는 다시 호출하지 않는다.
- **리사이즈:** 이미지의 긴 변을 약 1500px로 줄인다.
- **처리 방식:** 3장씩 병렬로 처리하고 진행률을 표시한다. 한 장이 실패해도 나머지는 계속 처리한다.
- **호출 제한 대응:** 429 오류가 나면 지수 백오프로 재시도한다. 그래도 실패하면 수동 입력으로 넘긴다.
- **배포 보호:** 데모 비밀번호 1개(st.secrets)와 1회 업로드 최대 30장으로 키 한도 소진을 막는다.
- **무료 등급 데이터 정책:** 입력이 서비스 개선에 쓰일 수 있다. 1일차에 약관을 확인하고 README와 업로드 화면 안내에 반영한다.
- **민감정보:** 카드번호를 추출하지 않는다. 업로드 이미지는 디스크에 저장하지 않는다. EXIF는 제거한다.

## 안정성 방어 (시연 대상)
- **영수증이 아닌 이미지:** `not_receipt`로 판정하고 제외하며 안내한다.
- **API 문제:** 키 누락·호출 실패·429 오류가 나면 안내하고, 재시도하거나 수동 입력으로 넘긴다.
- **빈 상태:** 업로드 0장, 참석자 0명, 한 결제 건의 참석자가 전원 해제된 경우 진행을 막고 안내한다.
- **중복 의심:** 같은 금액이 ±10분 안에 있으면 경고하고, 하나를 제외할 체크박스를 둔다.
- **민감정보:** 카드번호 미추출, 이미지 미저장, 외부 전송 고지

## 발표에서 보여 줄 것 (가이드 6단 구성)
1. **문제 정의:** 총무의 수작업 정산 시간과 실수 사례
2. **시연:** 일괄 업로드 → 카페에 빠진 사람 해제 → 결제자 변경 → 송금 메시지 복사 → 경로 지도
3. **설계 판단**
   - 영수증 단위로 참석자를 지정한 이유
   - 공식 하나로 두 정산 방식을 처리한 이유
   - Gemini Flash를 고르고 로컬 모델을 미룬 이유(배포)
   - 뺀 기능
4. **평가 리포트:** 프롬프트 v1/v2 비교표(정확도·응답 시간·오류율), 실패 사례 분석
5. **AI 활용:** 프롬프트 변경 기록, CLAUDE.md·스킬 활용, AI 실수를 고친 사례(`docs/ai-log.md`)
6. **회고:** 한계(환율, 품목 단위, 로컬 모델)와 다음 단계

### 작업 공간 하나의 사용 흐름
1. **만들기**: Orca 사이드바에서 새 작업 공간을 만든다. 또는 `orca worktree create --name feat-settlement --no-parent --agent claude --prompt "<구현 계획의 해당 태스크>"`
2. **셋업**: `scripts/setup_worktree.sh`를 실행한다(0단계에서 만듦). `.venv`를 만들고, `pip install -r requirements.txt`를 하고, main 작업 공간의 `.env`를 복사한다. `.env`와 `.venv`는 git에 없어서 작업 공간마다 필요하다.
3. **화면**: 탭 1은 Claude Code, 탭 2는 `streamlit run app.py`(UI 작업일 때만). 앱은 Orca 내장 브라우저에서 연다. 포트는 `orca ports`로 확인한다.
4. **상태 표시**: 작업 공간 카드의 코멘트와 상태(in-progress, in-review)로 진행 상황을 본다.
5. **마무리**: 테스트가 통과하면 PR을 만들고 main에 머지한다. 다음 작업 공간은 최신 main에서 만든다.

## 3일 일정
- **1일차**
  - 테스트 영수증 수집·라벨링
  - GitHub 저장소 생성·연결
  - Gemini 키 발급, 약관 확인, 송금 링크 확인
  - 인식 v1 + 평가 스크립트
  - 정산 로직 + 테스트
  - 앱 뼈대(목 모드), CLAUDE.md 작성
- **2일차**
  - 앱 전체 흐름 완성, Streamlit Cloud 배포
  - v1 실패 분석 → 프롬프트 v2
  - (여유가 있으면) 지도
- **3일차**
  - 안정성 방어, 상호 테스트
  - v1/v2 측정
  - README·ai-log·발표 자료

## 검증
- `pytest tests/`: 선결제형, 회비형(남음/부족), 결제자 여러 명, 1원 단위 나머지 처리를 확인한다.
- `python eval/run_eval.py --prompt v1|v2`: 정확도·응답 시간·오류율 표를 실물과 직접 만든 샘플로 나눠 출력한다.
- `streamlit run app.py`: 테스트 영수증 10장 이상으로 업로드부터 송금 메시지까지 끝까지 확인한다. 배포 URL에서도 같은 흐름을 확인한다.
