> 상태: **제출본 (2026-11-03).** 아직 하지 못한 일은 맨 아래 "남은 기록 항목"에 적었다(Gemini 남은 5장, 실물 영수증 평가, 상호 테스트).

> 기간: 2026-11-01 ~ 2026-11-03

## 1. 프로젝트 개요

- **무엇을:** Travill. 여행 영수증과 예약 캡처를 여러 장 올리면 AI가 상호·일시·금액을 읽고, 결제 건마다 결제자와 참석자를 정해 정산한다. 사람별 송금 메시지와 여행 경로 지도를 보여 준다.
- **왜:** 여행이 끝나면 총무가 영수증 수십 장을 손으로 옮겨 적고, "카페에는 누가 빠졌지?"를 기억에 의존해 정산한다. 시간이 오래 걸리고 틀리기 쉽다.
- **형태:** Streamlit 앱. 로그인과 DB 없음. Streamlit Community Cloud 배포.

**v1 실패 3건 (로컬)**
- `s02.png` 호텔 예약 캡처: 결제일 `2026-10-11`을 체크인 시각과 합쳐 `2026-10-11T15:00`으로 읽었다.
- `s03.png` 렌터카 예약 캡처: 결제일 `2026-10-10`을 대여 시각과 합쳐 `2026-10-10T09:00`으로 읽었다.
- `s07.png` 돌아간 식당 영수증: 결제금액 96,000원 대신 바로 아래 `과세물품가액` 87,273원을 읽었다.

**v2에서 고쳐진 것과 남은 것:** `s03`과 `s07`은 고쳐졌다. `s02`는 여전히 체크인 시각을 결제 시각으로 읽는다.

**해석할 때 주의할 점**
- **표본이 작다:** 13장뿐이고 생성 이미지다. 실물 영수증은 넣지 않았다.
- **같은 이미지에서 고쳤다:** v2는 이 13장에서 본 실패를 보고 고쳤다. 같은 이미지로 잰 향상은 실제보다 크게 보일 수 있다(과적합).
- **시간 차이:** 장당 시간 차이(36.6초 → 22.9초)는 반복 측정하지 않아 프롬프트 효과로 볼 수 없다. 로컬 모델은 앞선 요청이 남아 있으면 느려진다.
- **이전 92.3%와의 차이:** 앞선 기록의 "v1 92.3%"는 생성 영수증을 실제 가게 영수증처럼 다시 만들기(#13, #22) 전 이미지로 잰 값이라 이 표와 비교하지 않는다.
- **Gemini 측정:** 첫 실행에서 분당 한도(429)에 걸려 재시도까지 하루 한도(20회)에 들어갔다. 그래서 `--interval`(한 장씩 간격 두고 부르기)을 평가 스크립트에 더했다. 지금까지 읽은 8장은 모두 맞았고, 나머지는 한도가 풀린 뒤 잰다.

**응답 형식 강제:** 프롬프트만으로 JSON을 기대하지 않는다. Gemini는 `response_schema`, Ollama는 `format`에 같은 `Receipt` 스키마를 넘기고, pydantic으로 한 번 더 검증한다. 형식이 틀리면 1회 재시도한다.

## 5. 단계별 AI 활용

### 기획 (11-01)
- **AI에게 시킨 것:** 가이드 PDF를 읽고 질문하기, 접근 방식 2~3개 비교, 설계 스펙(`docs/superpowers/specs/2026-11-01-trip-receipt-split-design.md`)과 19개 태스크 구현 계획(`docs/superpowers/plans/2026-11-01-trip-receipt-split.md`) 작성.
- **내가 판단한 것:**
  - 두 정산 방식(회비형·선결제형)을 모두 지원한다.
  - 참석자는 결제 건마다 정한다.
  - 비용 때문에 Gemini Flash를 쓴다.
  - 기능마다 작업 공간을 따로 쓰고 PR로 머지한다.
  - 해외·환율, 품목 단위 정산, 로그인은 뺀다.

### 구현 (11-01 ~ 11-02)
- **AI에게 시킨 것:** 계획대로 실패하는 테스트부터 쓰고 구현하기. 기능별 PR 만들기(#1~#10). 다른 작업 공간의 에이전트에게 일을 나눠 맡기고 결과 리뷰하기.
- **내가 판단한 것:**
  - 머지는 매번 내가 승인한다.
  - 디자인 방향(토스 원칙, 자체 색 "여권 초록")과 앱 이름(Travill)을 정했다.
  - 지도 기능을 넣었다.
  - PDF 안내를 한국어로 바꿨다.
- **AI가 계획과 다르게 직접 정한 것:** 단계 1B에서만 13건이었다(예: 이미지가 없는 정답 항목을 오류로 집계, 평가를 30장씩 나눠 실행). 전체 목록은 PR #3 본문에 있다.

### 화면 확인 (11-01 ~ 11-02)
- **AI에게 시킨 것:** Orca 내장 브라우저로 앱을 직접 조작하고 캡처하기(설정 → 업로드 → 검토 → 정산 → 지도). 안정성 체크리스트 8개 항목 시연과 캡처(`docs/stability.md`).
- **내가 판단한 것:** 화면이 목업 같다는 피드백을 줬고, PDF 영어 툴팁을 고치기로 정했다.

### 실제 키 확인 (11-02)

## 7. 키·개인정보를 다룬 방식

- **키 저장:** 키는 `.env`(git 제외)와 배포용 Streamlit Secrets에만 둔다. 채팅에 붙여 넣지 않았다.
- **키 확인 방식:** AI는 키 값을 출력하지 않았다. 길이, 형식, API 응답 상태만 확인했다. 대화 기록 파일 전체에서 실제 키 문자열을 찾아 0회임을 확인했다.
- **커밋하지 않는 것:** 실물 영수증 사진(`eval/images/real/`)과 평가 원본 결과(`eval/results/*.json`).
- **인식 프롬프트:** 카드번호·승인번호·전화번호를 출력하지 않게 한다. 스키마에도 그 필드가 없다.

## 8. 회고

> 초안이다. AI가 이 기록과 작업 결과를 근거로 먼저 쓰고, 내가 내 생각을 더하고 고친다.

### 잘된 점
- **규칙을 파일에 남기니 끝까지 지켜졌다.**
  - `CLAUDE.md`의 구조 규칙(`core/`는 streamlit을 모른다)과 키·실물 영수증 커밋 금지가 PR 30개 내내 유지됐다.
  - "머지할 땐 계속 묻고 해"를 메모리에 저장한 뒤로는 매번 승인을 받고 머지했다.
- **개선을 숫자로 확인했다.**
  - v1이 틀린 3건을 보고 v2 규칙 두 개를 더했고, 로컬 모델 기준 핵심 3필드가 76.9%에서 92.3%가 됐다.
  - "좋아진 것 같다"가 아니라 같은 13장으로 다시 재서 확인했다.
- **테스트가 회귀를 막았다.** 새 기능마다 실패하는 테스트를 먼저 써서 테스트가 404개가 됐다. 문구·디자인을 여러 번 바꿔도 정산 계산과 오류 처리가 깨지지 않았다.
- **배포는 API, 테스트는 로컬로 나눈 것이 맞았다.** 과금과 하루 한도 걱정 없이 평가와 시연 녹화를 여러 번 돌릴 수 있었다.
- **직접 써 본 것이 효과가 컸다.** 자동 확인이 놓친 버그(금액 옆 화살표가 안 눌림)를 내가 앱을 써 보다가 찾았다.

### 아쉬운 점
- **실물 영수증으로 평가하지 못했다.** 생성 영수증 13장뿐이라 v2의 향상은 같은 이미지에 맞춘 결과일 수 있다.
- **AI의 "됐다"를 바로 믿은 때가 있었다.**
  - 줄 전체가 눌린다는 보고와 달리 실제로는 왼쪽 100px만 눌렸다(사례 12).
  - 지도가 한쪽으로 치우친 화면이 캡처에 이미 찍혀 있었는데 한동안 지나쳤다.
  - 모델 이름과 무료 등급 여부를 확인하지 않은 안내(사례 8, 9)도 같은 종류다.
- **Gemini 비교를 끝내지 못했다.** 간격 없이 부른 첫 평가가 분당 한도에 걸렸고, 재시도까지 하루 한도에 들어가 13장 중 8장만 쟀다.
- **화면을 여러 번 나눠 고쳤다.** 디자인을 여러 PR(#12, #18, #23, #24)에 걸쳐 고쳤다. 처음에 레퍼런스와 화면 구성을 더 구체적으로 정했으면 한 번에 끝낼 수 있었다.
- **상호 테스트를 하지 못했다.** 다른 사람이 처음 써 보며 막히는 곳은 확인하지 못했다.

### 다음에 바꿀 점
- **실제 데이터를 첫날 확보한다.** 실물 영수증을 먼저 모으고 정답을 적은 뒤 기능을 만든다.
- **화면 확인은 사람이 실제로 누르는 곳에서 한다.** 버튼 가운데만 누르는 자동 확인으로 끝내지 않고, 휴대폰 실기기로도 본다.
- **외부 API는 한도와 비용을 먼저 확인한다.** 평가 스크립트에는 처음부터 호출 간격을 둔다.
- **디자인 방향은 처음에 고정한다.** 레퍼런스 화면 몇 장과 바꾸지 않을 원칙을 먼저 정하고 시작한다.
